# 08 · I2C 地址约定与 MPU-6050 移植案例

一个真实的 I2C 移植失败案例：同一颗 MPU-6050，软件模拟 I2C 与硬件 I2C 两种实现都没调通，项目因此搁置。事后诊断定位到根因是 **7-bit / 8-bit 地址约定混乱**——这是 I2C 器件移植最常见的坑，本文同时给出总线扫描等通用排查方法。

失败代码存档：`drivers/MPU6050_failed/`（`sw_i2c_attempt/` 软件版、`hw_i2c_attempt/` 硬件版，后者含一套基于中断的 HT32 I2C1 收发框架，框架本身有参考价值）。

## 案例

目标：把 STM32 教程例程（软件 I2C + OLED 显示 WHO_AM_I 与六轴数据）移植到 HT32F52352，引脚 PB7=SCL / PB8=SDA。现象：`MPU6050_GetID()` 读回 `0x00`/`0xFF`，OLED 显示错误 ID。

### 版本 A：软件模拟 I2C

GPIO 开漏 + 微秒延时逐位模拟，地址沿用例程的 `#define MPU6050_ADDRESS 0xD0`。

`0xD0` = 7 位地址 `0x68` 左移一位拼上写位（W=0）。软件模拟**一次发送完整 8 位地址字节**，所以 `0xD0` 这个值本身是对的，读操作用 `0xD0|0x01=0xD1` 也对。但器件无响应——问题不在这一层（见后文"深层原因"）。

### 版本 B：硬件 I2C1

改用 HT32 硬件 I2C1（中断驱动收发 + 超时计数）。驱动框架里的地址配置函数长这样：

```c
static void I2C1_TargetAddressConfig(HT_I2C_TypeDef* I2Cx, u16 I2C_Address, u32 I2C_Direction)
{
    I2Cx->TAR = (I2C_Address << 1) | I2C_MASTER_READ/WRITE;   // 驱动内部左移
}
```

**该框架期望调用者传入 7 位裸地址 `0x68`**。而实际代码里写的是：

```c
#define MPU6050_ADDRESS    0x1C  // 7-bit I2C address   ← 错误
```

`0x1C` 不是 MPU-6050 的任何地址。左移后总线上出现的是 `0x38`，器件永远不 ACK，读回垃圾值。

### 根因

| 版本 | 驱动期望的格式 | 实际填的值 | 判定 |
| --- | --- | --- | --- |
| 软件 I2C | 8 位地址（含 R/W 位） | `0xD0` | 值正确 |
| 硬件 I2C | 7 位地址（驱动内部再左移） | `0x1C` | **应为 `0x68`** |

同一个常量名 `MPU6050_ADDRESS`，在两份代码里是两种语义。从"照搬例程"切到"适配驱动框架"时，没有查器件手册确认 7 位地址，而是随手填了一个想当然的值，且没有独立渠道验证。

## 通用教训

### 1. 地址常量必须钉死语义

写驱动时在头文件里同时注明两种形式，并在使用处推导一遍：

```c
#define MPU6050_ADDR_7BIT   0x68   // AD0=GND。7位地址，交给内部左移的驱动
#define MPU6050_ADDR_8BIT_W (MPU6050_ADDR_7BIT << 1)      // 0xD0，软件位带发送用
#define MPU6050_ADDR_8BIT_R (MPU6050_ADDR_8BIT_W | 0x01)  // 0xD1
```

判断手头驱动期望哪种格式：看它的地址配置代码**是否自己左移/拼接读写位**——左移的传 7 位，不左移的传 8 位。

### 2. I2C 不通的第一反应：看总线，别改代码

本案例两个版本来回折腾时序延时，方向从一开始就偏了。正确的排查顺序：

1. **逻辑分析仪/示波器看波形**——START 后的第一个地址字节对不对、有没有 ACK（第 9 位被拉低）。地址错在波形上一目了然，30 秒定位；
2. 没有分析仪就**先做总线扫描**（见下）；
3. 确认物理层（接线、上拉电阻：模块通常板载 4.7k，裸芯片必须外接；HT32 引脚可启用内部上拉 `GPIO_PullResistorConfig(..., GPIO_PR_UP)` 作应急）；
4. 通信通了再谈寄存器：`WHO_AM_I`（MPU-6050 寄存器 `0x75`）读回 `0x68` 即物理层+地址全对。

### 3. 总线扫描：20 行代码定位地址问题

对 0x08~0x77 逐个发 `START + ADDR + STOP`，收集 ACK 的地址。思路如下（适配任意 I2C 驱动）：

```c
void i2c_bus_scan(void)
{
    for (uint8_t addr = 0x08; addr <= 0x77; addr++) {
        i2c_start();
        if (i2c_send_byte_and_check_ack(addr << 1))   // 写方向探测
            printf("found: 0x%02X (7-bit 0x%02X)\r\n", addr << 1, addr);
        i2c_stop();
    }
}
```

扫描出 `0x68` 就说明硬件、上拉、时序全部没问题，剩下的只是常量填错；什么都没扫到才需要怀疑接线/供电/上拉。**任何 I2C 调试都从扫描开始。**

### 4. 一次只改一个变量

从软件 I2C 换硬件 I2C 时，通信机制、地址格式、超时行为同时变化，任何一次失败都无法归因。正确顺序：先在目标平台上把软件 I2C 调通（验证器件与接线），再迁移硬件 I2C（验证驱动框架），每步只有一个变量。

### 5. I2C 不通检查清单

- [ ] 地址：7-bit 还是 8-bit 约定？与驱动匹配吗？（本文案例）
- [ ] 上拉电阻：模块板载？外部？内部上拉够不够（走线长/速率高时不够）？
- [ ] 接线：SCL/SDA 没接反？共地？
- [ ] 引脚：复用功能配置对吗？软件 I2C 读 ACK 时 SDA 切输入方向了吗？
- [ ] 供电与复位：器件上电时序（MPU-6050 唤醒寄存器 `PWR_MGMT_1`）；
- [ ] 总线锁死：从机拉死 SDA 时需要手动发 9 个时钟解锁（`hw_i2c_attempt/I2C1.c` 里有 `I2C1_check_lock()` 可参考）。

## 如果想救活本案例

1. `#define MPU6050_ADDRESS 0x1C` → `0x68`（`drivers/MPU6050_failed/hw_i2c_attempt/MPU6050.h`）；
2. 上电先跑总线扫描确认 `0x68` 应答；
3. `WHO_AM_I` 读回 `0x68` 后，再按 `drivers/MPU6050_failed/` 里的初始化序列（唤醒、DLPF、量程）走。
